Module 1API fundamentals

Lesson 1 of 7 · 12 min read

What an API is and how AI APIs work

An API (Application Programming Interface) is a contract that lets one piece of software ask another for something. Your app sends a request; the service sends back a response. AI APIs work the same way: you send a prompt, the provider runs the model on its servers, and you get the generated text back.

The anatomy of an AI API call

  • Endpoint — the URL you send requests to, for example a “messages” or “chat completions” endpoint.
  • API key — a secret that identifies your account and is used for billing. Treat it like a password: never put it in front-end code or a public repository.
  • Request body (JSON) — which model to use, your instructions and messages, optional tools, and limits such as maximum output length.
  • Response — the generated content, why the model stopped, and a usage section counting input and output tokens.

SDKs

Providers publish official SDKs — libraries for Python, TypeScript, Java and more — that wrap the raw HTTP calls, handle retries and give you typed objects. Use them instead of hand-writing HTTP requests.

Rate limits

Every provider caps how many requests and tokens you can use per minute. Plan for it: retry with back-off on “too many requests” errors, and request higher limits before a big launch.

Key takeaways
  • Request → model runs on the provider’s servers → response.
  • Keys are secrets; responses report token usage.
  • Use official SDKs; plan for rate limits.

Capabilities to compare across providers

Most frontier APIs now offer a similar menu. Knowing the vocabulary makes vendor comparisons much easier.

  • Model tiers — a most-capable model, a balanced model and a fast, cheap model.
  • Context window — how much text fits in one request (frontier models: up to around a million tokens).
  • Multimodal input — images, PDFs, audio or video alongside text.
  • Tool use / function calling — the model can call functions you define; the foundation for agents.
  • Structured outputs — responses guaranteed to match a JSON schema.
  • Caching — repeated prompt prefixes billed at a discount.
  • Batch processing — asynchronous jobs at a lower price.
  • Grounding / web search — answers backed by live search results.
  • Data handling — retention, training use and regional processing.

The headline benchmark matters less than you’d think. For most products the deciding factors are quality on your own examples, cost per completed task, latency, data terms and how well the API fits your stack.

Key takeaways
  • Compare tiers, context, multimodality, tools, structured output, caching, batch, grounding and data terms.
  • Test quality on your own examples, not just benchmarks.

The Claude API (Anthropic)

Anthropic’s Claude API is built around one main endpoint, the Messages API. Tools, structured outputs and documents are all features of that endpoint, with supporting endpoints for batches, files, token counting and listing models.

Model line-up (October 2026)

  • Claude Opus 5.5 — the flagship for complex reasoning, coding and agents ($4 / $20 per million input / output tokens).
  • Claude Sonnet 5.5 — fast and capable for everyday coding, agent and enterprise work ($2 / $10).
  • Claude Haiku 5.5 — the fastest, cheapest tier for high-volume tasks ($0.10 / $0.50 for prompts up to 100K tokens).
  • Claude Fable 5.1 — Anthropic’s most capable widely released model, for the hardest long-horizon work ($10 / $50).

Current models offer a context window of up to 1 million tokens.

Notable capabilities

  • Adaptive thinking and effort — the model decides how much to reason; you tune depth and spend with an effort setting.
  • Tool use — your own tools, plus Anthropic-hosted web search, web fetch and code execution.
  • Prompt caching and the Message Batches API (50% cheaper) for cost control.
  • Citations on documents, and PDF and image input.
  • Managed Agents — Anthropic runs the agent loop and a sandboxed workspace for you.

Where to access it

Directly through Anthropic’s API, or through cloud platforms including Amazon Bedrock, Google Cloud Vertex AI and Microsoft Foundry — useful when your company already buys from one of them.

Prices change; check Anthropic’s pricing page before you commit.

Key takeaways
  • One Messages API with tools, structured output, caching and batches.
  • Tiers: Haiku (cheap) → Sonnet → Opus → Fable (most capable).
  • Available directly or via Bedrock, Vertex AI and Foundry.

The Gemini API (Google)

Google offers Gemini models through two front doors that share the same Google GenAI SDK:

  • Gemini Developer API via Google AI Studio — sign up with an API key; Google recommends it for most developers.
  • Vertex AI on Google Cloud — for enterprise controls, Cloud identity and regions, and integration with the rest of Google Cloud.

Model line-up (October 2026)

  • Gemini 3.1 Pro (preview) — complex reasoning, agents and coding.
  • Gemini 3.8 Flash — Google’s most capable Flash model, recommended for most new projects.
  • Gemini 3.5 Flash-Lite — the fastest, cheapest tier for high volume.

These models accept text, images, video, audio and PDFs, with a context window of about 1 million input tokens.

Notable capabilities

  • Function calling, structured outputs, code execution and context caching.
  • Grounding with Google Search and Google Maps — a distinctive strength for questions that need fresh information.
  • Batch processing at 50% of standard prices.
  • A free tier for Flash and Flash-Lite. Note: on the free tier, content may be used to improve Google’s products; on the paid tier it is not.

Pricing snapshot

Per million tokens on the paid tier: 3.8 Flash $0.75 input / $3.75 output (Google has announced these double on 1 January 2027); 3.5 Flash-Lite $0.30 / $2.50; 3.1 Pro $2 / $12 for prompts up to 200K tokens.

Key takeaways
  • Two routes: AI Studio (simple) or Vertex AI (enterprise).
  • Pro, Flash and Flash-Lite tiers; strong multimodal and Search grounding.
  • A free tier exists — check its data terms.
Lesson 5 of 7 · 14 min read

NVIDIA APIs and open models

NVIDIA plays a different role from Anthropic and Google. Rather than offering only its own models through a hosted API, it provides the infrastructure to run many models — including open-weight models you can host yourself.

NVIDIA NIM

NIM (NVIDIA Inference Microservices) packages models as optimised containers that run on NVIDIA GPUs — in any cloud, your own data centre or a workstation. NIM exposes OpenAI-compatible endpoints, so apps written for that common format can switch to a NIM-served model with minimal code changes.

The API catalog (build.nvidia.com)

NVIDIA hosts a catalog of models you can call over an API for prototyping. It includes NVIDIA’s own models and many third-party open-weight models — Llama, Mistral, DeepSeek, Qwen, Gemma, gpt-oss and others. Joining the free NVIDIA Developer Program gives access to hosted endpoints for prototyping and to self-hosted NIM for research and testing.

Going to production

Self-hosting NIM in production requires an NVIDIA AI Enterprise licence, priced per GPU (NVIDIA’s FAQ lists from $4,500 per GPU per year, with a 90-day trial). Alternatively, many inference providers serve the same open models and charge per token.

Nemotron: NVIDIA’s own models

The Nemotron family comes in Nano, Super and Ultra sizes, for everything from lightweight sub-agents to the hardest reasoning. NVIDIA publishes the weights, and its Nemotron Open Model License allows commercial use. Licences can vary by model, so always read the model card.

Other NVIDIA tools you may hear about

  • NeMo — a framework for training and fine-tuning generative models, plus guardrail and retrieval components.
  • Riva — GPU-accelerated speech recognition and text-to-speech.
Key takeaways
  • NVIDIA provides infrastructure to run many models, not one hosted model.
  • NIM: GPU-optimised containers with OpenAI-compatible endpoints.
  • Free to prototype; production self-hosting needs an AI Enterprise licence.

Module 3Choosing the right option

Lesson 6 of 7 · 12 min read

Open-weight models vs proprietary APIs

Open-weight is not always open-source

An open-weight model publishes its trained weights so you can download and run it. That is not the same as open-source in the strict sense, which also covers licence freedoms and often the training data and code. Many “open” models use custom licences with conditions. Read the licence before you build on one.

The trade-offs

Proprietary API (Claude, Gemini)Open-weight, self-hosted (e.g. via NIM)
SetupMinutes — get a key and call itGPUs, containers, scaling and updates to run
Cost shapePay per token; no fixed costFixed GPU and licence costs; can be cheaper per call at high, steady volume
Data controlGoverned by the provider’s terms and tierData stays on infrastructure you control
CapabilitiesFrontier models plus hosted extras (search, caching, agents)Depends on the model; you build the extras
CustomisationPrompting; limited fine-tuningFull control, including fine-tuning

Many companies use both: a proprietary frontier model for the hardest, highest-value tasks, and an open model for high-volume or data-sensitive workloads.

Key takeaways
  • Open-weight ≠ open-source; always read the licence.
  • APIs: fast start, pay-per-use. Self-hosting: control, fixed costs, ops burden.
  • Many teams mix both.
Lesson 7 of 7 · 12 min read

A vendor evaluation framework

Choosing an AI provider is a product decision. Use a simple, repeatable process.

  1. Define the job. Write down the task, inputs, expected outputs and quality bar.
  2. Build a small eval. 20–50 real examples with a clear definition of a good answer.
  3. Shortlist two or three options — for example, a Claude tier, a Gemini tier and an open model via NIM.
  4. Run the eval on each. Score quality, and record latency and token usage.
  5. Calculate cost per completed task at your expected volume, including caching and batch discounts.
  6. Check the non-functionals: data retention and training terms, regional processing, compliance, rate limits, SLAs and support.
  7. Consider switching cost. Keep prompts and evals portable, and isolate provider-specific code behind one module.
The “best model” is the one that meets your quality bar on your examples at the lowest cost per completed task, with data terms your company accepts.

Re-run the evaluation every few months. New models launch constantly, and prices move in both directions.

Key takeaways
  • Evaluate on your own examples, not leaderboards.
  • Compare cost per completed task and data terms.
  • Keep prompts and evals portable; re-evaluate regularly.
