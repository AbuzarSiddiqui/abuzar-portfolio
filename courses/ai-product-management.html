Module 1What’s different about AI products

Lesson 1 of 5 · 12 min read

Probabilistic products

Traditional software is deterministic: the same input gives the same output, and a bug is a bug. AI products are probabilistic: the same input can produce different outputs, and “mostly right” is the normal state.

What that changes for a PM

  • Quality is a distribution, not a checkbox. You don’t ask “does it work?” but “how often is it good enough, and how bad are the failures?”
  • Specs need examples. “Summarise the ticket well” is not testable. Twenty example tickets with what a good summary looks like is.
  • Failure design is product design. What the user sees when the AI is wrong or unsure matters as much as the happy path.
  • Costs scale with usage. Every call has a marginal cost, so unit economics are part of the product spec.
  • The ground keeps moving. New models arrive every few months; a feature that was impossible last quarter may be easy now.
Key takeaways
  • AI quality is a distribution — manage how often and how badly it fails.
  • Specs need concrete examples.
  • Failure UX and unit economics are part of the product.

Module 2Discovery: choosing the right problems

Lesson 2 of 5 · 14 min read

Where AI fits — and where it doesn’t

The most common AI product mistake is starting from the technology: “we should add AI”. Start, as always, from the problem.

Good signs a problem suits AI

  • The work involves language, images or messy unstructured data — reading, summarising, classifying, drafting.
  • A “mostly right, quickly” answer beats a perfect answer slowly, and a human can review cheaply.
  • The task is frequent and repetitive enough that small savings compound.
  • Information is scattered across tools and someone spends hours stitching it together.

Warning signs

  • Errors are costly and hard to detect.
  • A simple rule or a better form would solve it.
  • There is no data to ground the model in.

Example: the AI PM Agent

Product managers spend hours stitching together Jira, QA spreadsheets and meeting notes before every sprint review. The information already exists; the problem is attention. That made it a strong AI fit: unstructured inputs, frequent work, cheap human review — and a clear rule that the agent drafts but never changes Jira without approval.

Key takeaways
  • Start from the problem, not the technology.
  • Good fits: unstructured data, frequent tasks, cheap review.
  • If a rule or a form solves it, don’t use AI.

Module 3Specs, evals and trust

Lesson 3 of 5 · 14 min read

Evals are the new spec

An eval is a set of example inputs with a way to judge the outputs. For AI features, evals are the closest thing to a spec — and the main tool for knowing whether a change made things better or worse.

Building a first eval

  1. Collect 20–50 real examples covering common cases, edge cases and known failures.
  2. Define “good” for each — an expected answer, a checklist, or a rubric.
  3. Choose a grading method: exact match for structured outputs, code checks for formats, human review or a model-as-judge with a clear rubric for open-ended text.
  4. Run it on every change — new prompt, new model, new tool — and track the score over time.

Acceptance criteria for AI behaviour

Write criteria that can be checked against the eval, for example:

  • Given a sprint with stories missing acceptance criteria, when the PM asks for a health check, then every flagged story is listed with its ticket ID.
  • Given a question the connected data can’t answer, then the assistant says so instead of guessing.
Key takeaways
  • Evals = examples + a way to judge outputs.
  • Start with 20–50 real examples and run them on every change.
  • Write acceptance criteria you can test against the eval.
Lesson 4 of 5 · 12 min read

Designing for trust

Users adopt AI features they can trust and abandon the ones that burn them once. Trust is designed, not hoped for.

Patterns that build trust

  • Show the evidence. Cite the ticket, row or document behind every claim, one click away.
  • Admit uncertainty. “I’m not sure whether this belongs to PAY-112 or PAY-118” beats a confident wrong answer.
  • Drafts before actions. Let AI prepare; let humans approve anything irreversible.
  • Easy correction. Make it effortless to edit, reject or undo — and learn from those signals.
  • Set expectations. Tell users what the feature is good at and where to double-check.

Avoid

  • Over-claiming in marketing — the first visible mistake costs more trust than it would have otherwise.
  • Hiding the AI — users should know when content is generated.
Key takeaways
  • Cite evidence and admit uncertainty.
  • Drafts before actions; humans approve the irreversible.
  • Make correction effortless and learn from it.

Module 4Shipping and measuring

Lesson 5 of 5 · 14 min read

Rollout, metrics and iteration

Roll out in stages

  1. Internal dogfooding — the team uses it daily and logs failures.
  2. Limited beta with friendly users and close feedback.
  3. Gradual rollout with monitoring, a kill switch and a fallback to the non-AI path.

Measure four things

  • Quality — eval scores, plus real-world task success: was the draft accepted? Was the answer correct?
  • Adoption and retention — do people come back to the feature after the novelty wears off?
  • Trust signals — edit rates, rejection rates, “report a problem” clicks.
  • Cost per completed task — against the value each task creates.

Close the loop

Every rejected draft and corrected answer is a free eval case. Feed real failures back into your eval set, fix, re-run and ship again. And re-test when new models launch — the best improvement to your product might be one model upgrade away.

Key takeaways
  • Dogfood → beta → gradual rollout with a kill switch.
  • Measure quality, adoption, trust and cost per task.
  • Turn real failures into eval cases; re-test on new models.
