Module 1Tokens and pricing

Lesson 1 of 6 · 12 min read

How AI pricing works

Almost every AI API charges per token, priced per million tokens (MTok), with separate rates for:

  • Input tokens — everything you send: system prompt, instructions, documents, conversation history, tool definitions.
  • Output tokens — everything the model writes back, including any reasoning it does. Output is typically several times more expensive than input.

A worked example

At the time of writing, Anthropic lists Claude Sonnet 5.5 at $2 per MTok input and $10 per MTok output, and Claude Haiku 5.5 at $0.10 / $0.50. A request with 10,000 input tokens and 1,000 output tokens on Sonnet 5.5 costs:

10,000 × $2/1M + 1,000 × $10/1M = $0.02 + $0.01 = $0.03

Three cents sounds trivial — until a feature makes a million calls a month. Then it is $30,000, and the levers in this course matter.

Hidden input: the conversation

In a chat or agent, the whole history is sent again on every turn. Turn 20 of a conversation re-sends turns 1–19. This is why long conversations and agent loops get expensive — and why caching (next module) is so effective.

Prices change often — always confirm current rates on the provider’s pricing page before you build a business case.

Key takeaways
  • You pay per million tokens, input and output separately.
  • Output usually costs several times more than input.
  • Chats and agents re-send history every turn.
Lesson 2 of 6 · 8 min read

Counting and estimating tokens

Rules of thumb

For English text, a token is roughly three-quarters of a word, so 1,000 tokens is about 750 words. Code, numbers and non-English languages often use more tokens per word. Rules of thumb are fine for a rough business case, but never for billing-critical maths.

Measure, don’t guess

  • Providers offer token-counting endpoints — for example, Anthropic’s API has a count-tokens endpoint that returns the exact input count for a request before you send it.
  • Every API response reports usage: input tokens, output tokens and, where relevant, cached tokens. Log these per request.
  • Different models can tokenise the same text differently, so re-measure when you switch models.

Build a token profile

For each feature, record the typical input size, output size and number of calls per task. That profile tells you where the money goes — and which lever to pull first.

Key takeaways
  • ~750 words ≈ 1,000 tokens in English, as a rough guide.
  • Use token-counting endpoints and logged usage for real numbers.
  • Profile each feature: input, output, calls per task.

Module 2The free wins

Lesson 3 of 6 · 14 min read

Prompt caching

Many requests start with the same long prefix: a big system prompt, tool definitions, a reference document, the earlier part of a conversation. Prompt caching lets the provider store that prefix so later requests read it at a steep discount instead of paying full price again.

The economics (Anthropic’s API, at the time of writing)

  • Writing to the cache costs a little more than normal input — about 1.25× for the default 5-minute cache.
  • Reading from the cache costs a fraction — around 0.1× of the normal input price on most models, and less on some newer ones.
  • With the 5-minute cache, the second request already breaks even. Every request after that is mostly savings.

How to get cache hits

  • Stable content first, changing content last. Caching matches the prefix exactly; one changed character invalidates everything after it.
  • Watch for silent cache-breakers — a timestamp in the system prompt, tools listed in a different order, per-request IDs near the top.
  • Verify with usage data. If the cached-read count stays at zero across repeated requests, something is breaking the prefix.

Google’s Gemini API offers context caching too. The details differ by provider, but the principle is the same: never pay full price twice for the same prefix.

Key takeaways
  • Cache the long, stable prefix; read it back at a fraction of the price.
  • Put stable content first and changing content last.
  • Verify cache reads in usage data — zero means a cache-breaker.
Lesson 4 of 6 · 12 min read

Batching and prompt hygiene

Batch what nobody is waiting for

Not every request needs an instant answer. Nightly report generation, bulk tagging of feedback, evaluating thousands of test cases — these can wait minutes or hours. Batch APIs process such jobs asynchronously at a discount; Anthropic’s Message Batches API, for example, costs 50% less than standard requests.

Input hygiene

  • Send only the context the task needs — retrieve the three relevant documents, not the whole wiki.
  • Trim prompts written for older models: long lists of “ALWAYS” and “NEVER” rules are often unnecessary now and can even reduce quality.
  • Drop tool definitions a route never uses.

Output hygiene

  • Ask for the format you need — “return JSON with these three fields” instead of a friendly essay.
  • Use structured outputs where available so you don’t pay for retries on malformed responses.
  • Set sensible maximum output lengths per route.

Loop hygiene for agents

Agents can waste tokens by re-reading the same files or making redundant tool calls. Give them clear goals, the right tools, and stopping conditions.

Key takeaways
  • Batch non-urgent work for big discounts (50% on Anthropic’s Batches API).
  • Send only the context the task needs.
  • Ask for compact, structured outputs.

Module 3Trade-offs and measurement

Lesson 5 of 6 · 12 min read

Effort, model choice and routing

After the free wins come the levers that trade some capability for cost. Pull them deliberately, with measurement.

Effort level

Modern models let you control how hard they think. On Anthropic’s current models this is the effort setting (low, medium, high, xhigh, max). Lower effort means less reasoning and fewer tokens. Chat, classification and high-volume routes often do well at low effort; complex coding and long agentic tasks benefit from higher effort.

Model choice

Providers offer tiers — for Claude, Haiku (fastest, cheapest), Sonnet (balanced) and Opus (most capable), with prices differing by an order of magnitude or more. Use the smallest model that meets your quality bar for that route.

Routing — and its hidden cost

You can send easy requests to a cheap model and hard ones to a strong model. But first test the simpler alternative: the strong model at lower effort. Newer models at low effort often match older models at high effort, and one model means one cache — caches don’t carry across models.

Judge cost per completed task, not per request. A cheap request that needs three retries isn’t cheap.
Key takeaways
  • Effort and model tier are the main quality-for-cost levers.
  • Try the strong model at low effort before building a cascade.
  • Optimise cost per completed task, not per request.
Lesson 6 of 6 · 10 min read

Measuring cost and setting budgets

The metric that matters: cost per completed task

Divide total AI spend for a feature by the number of tasks it successfully completed — tickets drafted and accepted, questions answered correctly, documents processed. This captures retries, failures and wasted calls that per-request averages hide.

What to log

  • Per request: model, input tokens, output tokens, cached tokens, latency, feature/route.
  • Per task: number of calls, total tokens, outcome (success, failure, human-corrected).

Unit economics

Compare cost per task with the value of the task: the minutes saved, the revenue enabled, the support ticket avoided. If an AI feature costs ₹4 per task and saves ten minutes of a ₹1,000-per-hour analyst, the case is easy. If it costs more than the value it creates, optimise or rethink.

Budgets and guardrails

  • Set spend alerts and per-feature budgets.
  • Cap agent loops with step or token budgets so a runaway task can’t burn money.
  • Re-run your measurements after every prompt or model change — costs drift.
Key takeaways
  • Track cost per completed task, per feature.
  • Compare it with the value each task creates.
  • Use alerts, budgets and loop caps; re-measure after changes.
